# 显存调优（RTX 5080 16GB 实操手册）

这份文档解决一个问题：**在 16GB 显存、还要同时跑语音模型的前提下，怎么让本地大模型又快又不崩。**

所有数字都是估算模型，请以你自己机器的实测为准——下面的方法就是教你怎么测。

---

## 一、先搞清楚预算

打开一个 PowerShell 窗口，什么都不启动的情况下先看基线：

```powershell
nvidia-smi --query-gpu=memory.total,memory.used,memory.free --format=csv
```

典型结果：`16303 MiB, 3453 MiB, 12850 MiB`

也就是说 **16GB 卡实际只有约 12.5GB 可用**（桌面、浏览器、通讯软件占了 3.4GB）。
关掉浏览器和微信能多挤出 1~2GB，值得做。

### 各项开销的估算

| 项目 | 27B Q4_K_M | 14B Q4_K_M | 9B Q4_K_M |
|---|---|---|---|
| 权重 | ~16.5GB | ~9.0GB | ~5.6GB |
| KV cache @8K ctx, q8_0 | ~0.7GB | ~0.4GB | ~0.3GB |
| KV cache @16K ctx, q8_0 | ~1.4GB | ~0.8GB | ~0.6GB |
| 计算缓冲 + CUDA 上下文 | ~0.9GB | ~0.7GB | ~0.6GB |
| **全量入显存合计 @8K** | **~18.1GB ✗** | **~10.1GB ✓** | **~6.5GB ✓** |

结论一目了然：**14B 以下能全量进显存，27B 必须分层卸载。**

---

## 二、27B 档位：怎么调 `--n-gpu-layers`

27B 大约 49 层。默认配置 28 层在 GPU，其余 21 层在内存，靠 PCIe 每 token 搬运一次。
**层数越多越快，但一旦超出显存就会触发 OOM 或驱动回退到共享内存——那会让速度掉到 1 tok/s 以下，
比少放几层还慢。** 所以要"贴着上限但留余量"。

### 调优流程（20 分钟，一次调好）

```powershell
# 1) 关掉浏览器/通讯软件，确认空闲显存
scripts\stop.ps1
nvidia-smi --query-gpu=memory.free --format=csv

# 2) 用当前默认层数启动
scripts\start-models.ps1

# 3) 立刻看显存（模型加载完那一刻）
nvidia-smi --query-gpu=memory.used,memory.free --format=csv

# 4) 测真实速度
scripts\verify.ps1 -Bench
```

判读规则：

| 观察 | 结论 | 动作 |
|---|---|---|
| `memory.free` > 1200 MiB 且生成正常 | 还有余量 | `-NGpuLayers` **+3**，重测 |
| `memory.free` 在 400~1200 MiB | 差不多是甜点 | 保持 |
| `memory.free` < 300 MiB | 太挤了 | `-NGpuLayers` **-3** |
| 日志里有 `CUDA error: out of memory` | 超了 | `-NGpuLayers` **-4** 起 |
| 速度突然掉到 1~2 tok/s 但显存没满 | 驱动在做显存/内存换页 | `-NGpuLayers` **-4** |

```powershell
# 例如每次加 3 层
scripts\stop.ps1
scripts\start-models.ps1 -NGpuLayers 31
nvidia-smi --query-gpu=memory.used,memory.free --format=csv
scripts\verify.ps1 -Bench
```

把最终稳定的数字写进 `config/models.json` 里 `quality-27b` 的 `n_gpu_layers`，
以后 `start-models.ps1` 就默认用它。

### 如果还想更快

按收益从大到小：

1. **换 14B 档位**（速度 ×5~8）——最有效的一步，日常使用强烈建议
2. **缩短上下文**：`context_tokens: 4096`，KV cache 减半，省下的显存可以多放几层
3. **减少对话轮数**：长会话会让 KV cache 增长。定期新建会话（记忆不会丢，长期记忆是独立的）
4. **关掉占显存的软件**：浏览器硬件加速是显存大户

## 三、语音模型的显存共存

这是本机最容易踩的坑：**27B 已经吃满显存时，语音模型加载会失败。**

系统对此的处理方式是：

| 机制 | 行为 |
|---|---|
| STT 懒加载 | 第一次语音输入才加载 Whisper（int8 ≈1.6GB） |
| STT 空闲卸载 | 默认 900 秒没有语音输入就释放显存 |
| STT CPU 回退 | GPU 加载失败时自动改用 CPU int8（慢但可用） |
| TTS 本地优先 | IndexTTS2 不可用时切在线音色（零显存） |
| TTS 空闲卸载 | 默认 600 秒无合成就释放 |

配置在 `config/config.yaml → speech`：

```yaml
speech:
  stt_idle_unload_s: 900     # 改成 300 可以让显存更快还给大模型
  tts_preference: [indextts, edge, sapi]
```

**27B 档位的实用建议**：把 `tts_preference` 设成 `[edge, sapi]`，语音识别改成
`stt_device: cpu` + `stt_compute_type: int8`。这样 GPU 完全留给大模型，
语音走 CPU（9800X3D 跑 int8 Whisper 完全够快），是 27B 档位下体验最稳的组合。

```yaml
speech:
  stt_device: cpu
  stt_compute_type: int8
  tts_preference: [edge, sapi]
```

等切到 14B 档位后再把语音放回 GPU：

```yaml
speech:
  stt_device: cuda
  stt_compute_type: int8_float16
  tts_preference: [indextts, edge]
```

## 四、上下文长度的取舍

`config.yaml → llm.context_tokens` 直接决定 KV cache 大小，而 KV cache 与权重抢显存。

| context_tokens | KV cache(q8) | 适合 |
|---|---|---|
| 4096 | ~0.4GB | 27B 档位想多放两层 GPU |
| 8192（默认） | ~0.7GB | 通用 |
| 16384 | ~1.4GB | 14B 档位长对话 |
| 32768 | ~2.8GB | 9B 档位 |

**注意**：上下文 ≠ 记忆。超出上下文的历史轮次会被中间裁剪（并留下"此前有 N 条未展示"的提示），
而**长期记忆是独立的，不受上下文长度影响**。所以不要为了"记住更多"而盲目加大 context。

## 五、模型文件位置的契约

所有模型权重都在项目目录内的 `models\` 下（即 D 盘）：

```
models\
├─ gguf\       主模型 + 嵌入 + 重排（download-models.ps1）
├─ whisper\    faster-whisper（首次使用时自动下载）
├─ tts\        IndexTTS2
├─ voices\     音色克隆参考音频
└─ cache\      临时缓存
```

这个契约由代码强制，不是约定：`core/config.py::Paths.assert_on_project_root()` 会对
任何指向项目根之外的模型路径直接抛错。想搬到别的盘，改 `config/local.yaml` 的 `paths.root`。

## 六、性能正常值参考（用于判断"是不是坏了"）

| 档位 | 首字延迟 | 生成速度 | 说明 |
|---|---|---|---|
| 27B Q4，28 层 GPU，8K ctx | 3~8s | 4~8 tok/s | 提示词缓存命中后会明显更快 |
| 14B Q4，全量 GPU，16K ctx | 0.5~1.5s | 35~55 tok/s | 日常推荐的体感 |
| 9B Q4，全量 GPU，32K ctx | 0.3~0.8s | 60~90 tok/s | 语音对话几乎无等待 |
| Whisper large-v3-turbo int8 GPU | — | 5 秒语音 ≈ 0.3~0.8s | CPU int8 约 1~3s |
| 记忆检索（含嵌入+重排） | 80~300ms | — | 后台，不占生成时间 |

明显低于这些数字，先按上面第二节的流程排查显存，再看 `logs\llama-chat.log`。

## 七、日志怎么看

`logs\chatbot.jsonl` 每行一个 JSON，排查性能问题主要看这几个字段：

```json
{"msg":"consolidation pass finished","vectors_backfilled":0,"duplicates_merged":3,...}
```

* `"msg":"application started"` → 启动耗时、llm 后端
* `"msg":"llm stream open retry"` → 模型服务抖动
* `"msg":"memory superseded"` → 冲突消解实际发生了（说明记忆在自我修正）
* `"msg":"whisper model unloaded (VRAM released)"` → 显存归还生效

`logs\llama-chat.log` 里搜索 `offloaded` 可以看到实际卸载了多少层：

```
load_tensors: offloaded 28/49 layers to GPU
llama_kv_cache_init: CUDA0 KV buffer size = 512.00 MiB
```

**这两个数字就是调优的唯一事实来源**——比任何估算都准。
