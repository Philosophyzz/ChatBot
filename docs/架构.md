# 架构说明

面向要改这个项目的人（包括三个月后的你自己）。核心问题是：**为什么这么分层，
以及要加东西的时候应该动哪里。**

---

## 一、设计原则

1. **契约先于实现。** 每个能力都是一个 `typing.Protocol`（`src/core/types.py`），
   实现模块之间互不 import。换掉向量库不需要动记忆逻辑，换掉 TTS 不需要动对话引擎。
2. **失败要降级，不要崩。** 嵌入服务挂了用哈希嵌入、重排服务挂了用词法重排、TTS 本地挂了走在线、
   抽取模型挂了走规则。只有"对话模型不可用"是真正致命的，而它也会变成一条可读的错误事件。
3. **热路径不阻塞。** 记忆抽取、向量化、固化全在后台；语音模型空闲即卸载显存。
4. **可解释优于黑箱。** 每条检索命中都带评分拆解，每个组件都有 `health()`，
   每轮对话都有结构化日志。出问题时能定位到具体一层。
5. **数据可迁移。** 全部状态在一个 SQLite 文件里，拷走即备份。

## 二、分层视图

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层   web/   (原生 JS，无构建)     api/routes.py (REST/WS) │
├──────────────────────────────────────────────────────────────┤
│ 编排层   core/chat.py   一轮对话的完整生命周期                │
│          core/session.py 会话状态与 LRU 缓存                  │
├──────────────────────────────────────────────────────────────┤
│ 能力层   memory/  记忆    speech/  语音    persona/  人设     │
│          llm/     LLM/嵌入/重排                               │
├──────────────────────────────────────────────────────────────┤
│ 契约层   core/types.py (Protocol)   core/registry.py (插件)   │
│          core/config.py (配置)      core/errors.py (错误)     │
├──────────────────────────────────────────────────────────────┤
│ 存储层   SQLite (WAL) + FTS5 + float32 向量 blob              │
│          llama-server ×3 (对话 8080 / 嵌入 8081 / 重排 8082)   │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向向下。** 表现层不知道 SQLite 的存在，能力层不知道 HTTP 的存在。

## 三、一轮对话的完整时序

```
POST /api/chat  或  WS {action:"chat"}
   │
   ├─ app.chat_lock()                    ← 单卡单模型：并发只会互相拖慢，这里排队
   │
   └─ ChatEngine.stream_turn()
        ├─ SessionManager.get_or_create()      会话 + 人设绑定
        ├─ MemoryEngine.build_context()
        │     ├─ 候选池：一次性取出全部有效记忆（含时效过滤）
        │     ├─ 通道1 稠密向量  /v1/embeddings → 向量库暴力检索
        │     ├─ 通道2 BM25      FTS5 MATCH（含 CJK 子串 LIKE 兜底）
        │     ├─ 通道3 时序图谱  实体锚定 → 一跳关系扩展
        │     ├─ 融合：各通道 min-max 归一 × 权重 + 重要度 + 指数时间衰减
        │     ├─ 重排：/v1/rerank（失败静默跳过）
        │     ├─ 去重：近重复抑制（MMR-lite）
        │     └─ 装配：按 token 预算裁剪 → 渲染成提示词片段
        ├─ build_system_prompt()  人设 + 时间 + 记忆 + 语音约束
        ├─ _trim_history()        中间裁剪：保留系统提示与最近若干轮
        ├─ LLMBackend.stream()    SSE 解析 → Session/start/text/usage/done 事件
        ├─ 持久化 user + assistant 消息
        └─ MemoryEngine.remember_turn()  ← 入队即返回，不阻塞
                                          （后台 worker 做抽取/消解/落库）
```

事件类型（**所有通道共用同一套**）：`session` `memory` `memory_skipped` `start`
`reasoning` `text` `tool` `usage` `done` `error`。新增通道（桌面壳、CLI）只要消费这些事件即可。

## 四、记忆子系统的内部结构

```
memory/
├─ db.py            连接管理 / schema / 迁移（唯一写 SQL DDL 的地方）
├─ store.py         数据访问：会话·消息·记忆·实体·关系·档案·KV
├─ vector.py        向量索引（sqlite 暴力检索 / 内存版），VectorStore 契约
├─ extract.py       写入路径：LLM 抽取 → 归一 → 去重 → 冲突消解 → 落库
├─ retrieve.py      读取路径：三路召回 → 融合 → 重排 → 预算装配
├─ consolidate.py   维护路径：补向量 / 合并重复 / 摘要 / 反思 / 衰减
└─ engine.py        门面：把上面五个拼起来，并管理后台 worker
```

### 关键数据模型

`memory_items` 同时承担"事实表"和"时序图谱边"的角色：

| 字段 | 语义 |
|---|---|
| `kind` | episode / fact / preference / profile / relation / summary / reflection |
| `subject` `predicate` `object` | 结构化三元组（冲突消解靠它精确匹配同一槽位） |
| `valid_from` `valid_to` | **事件时间**有效性窗口，支持"截至某时刻"的点查 |
| `supersedes` `superseded_by` | 取代链，保留"我以前以为是怎样" |
| `importance` `confidence` | 重要度由抽取给出，之后由固化按召回情况调整 |
| `access_count` `last_access_at` | 召回强度，是衰减与增强的依据 |

`superseded_by IS NULL` 就是"当前有效"的判定条件。**删除默认是软删除**（关闭有效期窗口），
因为硬删除会让一条已被推翻的旧认知在某次抽取中重新出现。

### 冲突消解规则（`extract.py::_contradicts`）

按顺序判断，避免向量相似度单独决定"真值"：

1. 相似度 < 0.62 → 无关，不算冲突
2. kind 不兼容（偏好 vs 情景）→ 不算冲突
3. subject 都非空且不同 → 不算冲突
4. 同 `predicate`：`object` 不同 → **冲突**；`object` 相同 → 确认（增强，不新建）
5. 无结构化谓词时：相似度 ≥ 阈值且内容哈希不同 → 冲突

### 融合打分

```
score = w_dense·dense + w_lexical·lexical + w_graph·graph
      + w_importance·importance + w_recency·0.5^(age_days/half_life)
      + w_rerank·rerank + 0.45·is_profile
```

每个通道**先 min-max 归一化再乘权重**，否则量纲差异会让某个通道垄断排序。
通道内取值全部相同时贡献 0（而不是常数），避免制造隐性偏置。
所有权重在 `config.yaml → memory` 里，可在设置界面热改。

## 五、扩展指南：加一个能力

### 5.1 加一个 LLM 运行时（例如某个新推理引擎）

```python
# src/plugs/my_runtime.py
from core.registry import KIND_LLM, register

@register(KIND_LLM, "my_runtime")
class MyRuntime:
    name = "my_runtime"

    def __init__(self, base_url: str = "http://127.0.0.1:9000", model: str = "", **_):
        ...
    async def stream(self, request): ...      # yield TokenEvent
    async def complete(self, request): ...    # -> Completion
    async def health(self): ...               # -> dict
```

配置：`llm: { backend: my_runtime }`。
`AppConfig._build_llm` 会把 `base_url / model / api_key / timeout_s` 透传进来。

### 5.2 换向量库（数据量大了想上 pgvector）

实现 `VectorStore` 的五个方法（`upsert / search / delete / count` + 可选 `get / iter_all`），
注册为 `KIND_VECTOR_STORE`，然后在 `memory/engine.py` 的 `MemoryEngine.create()` 里
把 `registry.create(KIND_VECTOR_STORE, "sqlite", database)` 换成读配置的名字。
**记忆逻辑一行都不用改**，因为检索只依赖 `search()` 返回的 `(id, score)`。

### 5.3 加一个输入输出通道

```python
@register(KIND_CHANNEL, "desktop")
class DesktopChannel:
    name = "desktop"
    async def send(self, session_id: str, event: dict) -> None: ...
```

消费 `ChatEngine.stream_turn()` 产出的事件即可复用全部能力（记忆、人设、语音）。
这也是"先做 Web、预留桌面壳"能成立的原因。

### 5.4 加一个记忆抽取器

实现 `KIND_EXTRACTOR`，提供 `process_turn(...) -> ExtractionOutcome`。
比如用本地小模型专门做抽取、或用规则引擎做特定领域抽取。

## 六、并发与资源模型

| 资源 | 策略 | 原因 |
|---|---|---|
| GPU 生成 | `asyncio.Semaphore(1)` | 单卡跑大模型，并发只会让两个请求都变慢 |
| SQLite 写 | 进程内 `threading.Lock` + `BEGIN IMMEDIATE` | 写串行化，读走 WAL 不阻塞 |
| SQLite 读 | 同步执行（微秒级） | 走线程池反而更慢 |
| 记忆抽取 | `asyncio.Queue(256)` + 单 worker | 突发对话不会堆积成 CPU 风暴；队列满则丢弃并计数 |
| 固化 | 定时 + 空闲判定 + 互斥锁 | 绝不在用户说话时抢 GPU |
| STT/TTS 模型 | 懒加载 + 空闲卸载 | 用完把显存还给大模型 |
| 会话缓存 | LRU 64 个 | 长时间运行不会无限增长 |
| LLM 连接 | httpx 连接池复用 | 多轮对话省掉 TCP/TLS 开销 |

## 七、测试策略

`tests/` 不依赖 GPU、不下载任何权重——这是能反复回归的前提：

* `test_core.py` —— 配置优先级、路径契约、插件注册表、token 估算、文本清洗
* `test_memory.py` —— schema、去重、取代链、FTS 中文、实体别名、向量检索、
  JSON 容错解析、规则抽取、幂等性、冲突判定、预算裁剪、**嵌入服务挂掉后的降级**
* `test_engine_api.py` —— 人设 CRUD、语音路由回退、事件顺序、**跨会话记忆召回**、
  历史裁剪、后端故障转错误事件、REST/SSE 全接口冒烟

关键测试对应的是关键承诺：
`test_engine_persists_and_remembers_across_sessions`（跨会话记忆）、
`test_extraction_is_idempotent_per_message`（不重复抽取）、
`test_contradiction_supersedes_old_fact`（冲突消解）、
`test_retrieval_respects_token_budget`（预算不超）、
`test_memory_survives_embedder_failure`（降级不崩）。

```powershell
python -m pytest tests -v        # conda activate chatbot 之后
```
